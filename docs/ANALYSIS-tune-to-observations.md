# After tuning, how far is each code from the observations? (exploratory)

Generated by `scripts/explore_tune_to_observations.py`. For each observed curve on the dials page, each code's four dials are searched for the setting that reproduces it on the simulated mass bins it covers. The leftover is the root-mean-square difference in dex and in the page's noise units (1 = the scatter between one run of each code).

**This is not a test of either code.** An observed curve is defined differently from the simulated one (aperture, initial mass function, how galaxies are selected and counted), CAMELS boxes are small (25 Mpc/h) and the simulations are not calibrated to be compared at this level, so part of every leftover is definition, not physics. ## Reading

25 observed curves could be compared. Both codes get within one noise unit of 20; at least one does on 20. By property: black hole mass: TNG within one noise unit on 0 of 2; SIMBA within one noise unit on 0 of 2; stellar mass function: TNG within one noise unit on 14 of 15; SIMBA within one noise unit on 14 of 15; quenched fraction: TNG within one noise unit on 4 of 4; SIMBA within one noise unit on 4 of 4; specific SFR of star-forming galaxies: TNG within one noise unit on 2 of 3; SIMBA within one noise unit on 2 of 3; stellar metallicity: TNG within one noise unit on 0 of 1; SIMBA within one noise unit on 0 of 1. A smooth curve with a few bins is easy to fit with four dials, so being within one noise unit of the stellar mass function or the quenched fraction is weak evidence of anything; being far off, as for the black hole mass, is the informative outcome. A leftover over one noise unit says only that no setting of the four dials of that code reproduces the curve to the run-to-run scatter, which given the definition differences above is the expected state for many observations and says nothing against either code in particular.
