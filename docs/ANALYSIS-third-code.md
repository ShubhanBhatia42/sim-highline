# A third code: Astrid (exploratory)

Generated by `scripts/explore_third_code.py`, made **after** the registered all-at-once run. It is not part of that result and changes none of its verdicts. The question: does the picture change when the third CAMELS code is added, and which pair of codes is furthest apart on which property?

Method: the registered machinery (one polynomial emulator per code, differences measured in noise units, the dials of both codes searched for the smallest distance), run on each of the three pairs over the 97 outputs (26 blocks) that are usable in all three codes, so the pairs are comparable with one another. Distances are uncorrected point estimates, as in the registered point distance. The usable set is smaller than the registered two-code set whenever Astrid lacks an output, so the TNG–SIMBA number here is not the registered 4.8: the registered run used 186 outputs and gave 4.85; the comparison that matters here is between the three pairs on the same outputs.

Emulator degree per code: TNG 3, SIMBA 3, Astrid 3. Share of simulations with a finite value over the shared outputs: TNG 99%, SIMBA 99%, Astrid 98%.

## Reading

Over all shared observables the pairs are IllustrisTNG vs SIMBA 3.9, IllustrisTNG vs Astrid 1.5, SIMBA vs Astrid 3.4 noise units. The furthest pair is IllustrisTNG vs SIMBA and the nearest is IllustrisTNG vs Astrid.

Properties where one code stands apart (both of its pairs more than one noise unit apart, the other pair not): black hole occupation — SIMBA. With so few outputs in some of these properties, read this as a lead, not a finding.

Properties still more than one noise unit apart in **every** pair, after the best retuning of each (the candidates for a difference that is built into the codes' models and not a matter of dial settings): none.

A distance over one noise unit means the two codes' curves cannot be brought within the run-to-run scatter by turning the four dials, at the usual caveats: the dials are only four of the things that differ, the emulators have their own error (included in the noise scale) and the point estimate is not corrected for emulator noise, so small distances are upward-biased.
